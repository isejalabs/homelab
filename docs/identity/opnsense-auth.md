# OPNsense administrator login

The gateways `gw2` and `gw3` are not managed from this repository (see [`network.md`](../architecture/network.md#physical-network-opnsense-ucs-and-the-root-nameservers)), so this page records the decision, the proof of concept and the procedure for a login that is configured by hand in the web interface. Tracking: [#1730](https://github.com/isejalabs/homelab/issues/1730) (evaluation), [#2237](https://github.com/isejalabs/homelab/issues/2237) (this investigation), [#2238](https://github.com/isejalabs/homelab/issues/2238) (`bob-adm`), [#2239](https://github.com/isejalabs/homelab/issues/2239) (operator and read-only). The framing decision is [ADR 0016](../decisions/0016-identity-and-web-sso.md), points 8 and 9, which assumed that OPNsense can only bind LDAP; the proof of concept below shows a way to real OIDC, so the result here refines that point (a decision record is only written once the owner adopts it for production).

Account names on this page are placeholders under [ADR 0019](../decisions/0019-public-disclosure-policy.md): `bob-adm` is the owner's administrator account, `bob` the everyday one, and other users are not named. Log lines are quoted with the placeholder in place of the real name.

## Decision

Adopted by the owner on 2026-11-11 as [ADR 0020](../decisions/0020-opnsense-administrator-login.md); not yet applied in production. A proof of concept ran on `gw3` on 2026-11-10 (see [below](#oidc-with-os-sso-proof-of-concept-on-gw3)):

- **OIDC to the Keycloak realm `admin`** through the third-party plugin **os-sso**, for the web interface only. Keycloak owns the second factor (in the realm `admin`: the UCS password, then a WebAuthn passkey or key with TOTP as fallback, see [`keycloak-mfa.md`](keycloak-mfa.md)), so the cumbersome "token in front of the password" entry of OPNsense's own TOTP is not needed. This replaces the earlier LDAP + TOTP proposal as the preferred route, because LDAP + TOTP keeps the seed in every local user and needs the token typed into the password field.
- **`root` stays a local account** with the local second factor (as today: the server "Google Auth OTP" is the only entry in the login list of `gw3`). It is the break-glass login and is not touched.
- **Users are local accounts that the plugin owns**: created with the plugin's own writer (no usable password), bound to the Keycloak subject at the first login. Nothing is created automatically from the directory.
- **LDAP + TOTP stays documented** below as the alternative if the plugin is rejected (maintainer, age, review effort); it is the only route that needs no third-party code.
- **A Keycloak session skips the second factor.** An existing Keycloak SSO session (cookie) is accepted without a new factor, so an administrator who is already signed in to another application reaches the firewall without being asked. The plugin can send `max_age`, which makes Keycloak re-authenticate a session older than the given number of seconds, and can require an `acr`; setting `max_age` on the production server is part of the production steps. Not tested.
- **Dependency:** the firewall login depends on the production Keycloak (cluster, database, UCS federation), while the cluster's routing depends on the firewall. `root` + local TOTP breaks the loop; that is why it stays untouched.

## OIDC with os-sso: proof of concept on gw3

Goal of the proof of concept ([#2237](https://github.com/isejalabs/homelab/issues/2237), [#2238](https://github.com/isejalabs/homelab/issues/2238)): can a Keycloak login replace typing a password and a local token into the OPNsense login page, with `root` + local TOTP left as break-glass? Target `gw3`, the HA backup, so the master and the CARP addresses were never in the path. Run 2026-11-10 with the owner present and a second `root` session open.

**Why os-sso and not the other plugin.** Both are small third-party projects without a security track record. os-sso ([`MaximeWewer/os-sso`](https://github.com/MaximeWewer/os-sso), BSD-2-Clause, release `2026.11.1`) was preferred for the following: it enforces `max_age` and `acr`, never binds a login to an account with a real local password, never binds to a privileged account it did not create itself (a takeover guard), and keeps its providers in the ordinary authentication-server list (which the HA sync covers). These are the plugin's own claims; only the account binding was seen in action. The alternative, [`jpawlowski/opnsense-openid-connect`](https://github.com/jpawlowski/opnsense-openid-connect), is web interface only and was at `1.0.0-beta5`. The owner asked for os-sso to be proven; the other one was not installed.

**Supply-chain check done before installing.** The release package has no signed attestation, so it was compared with the tagged source: 85 of 85 files identical, and the three vendored libraries (`php-jwt`, `php-saml`, `xmlseclibs`) byte-identical with upstream at their pinned commits. `gw3` downloaded the package itself from the GitHub release and the SHA-256 matched the audited one. The installation changed nothing about the login (a config backup was taken first). Pushing the file with `scp` or over stdin from the Mac stopped after 32 KB (cause unknown), which is why the box fetched it itself.

**What was configured on `gw3`.**

| Part | Value |
| --- | --- |
| Keycloak client | `opnsense` in the realm `admin` of the dev Keycloak, code in [`terragrunt/non-prod/eu-central-1/dev/keycloak-realm/terragrunt.hcl`](../../terragrunt/non-prod/eu-central-1/dev/keycloak-realm/terragrunt.hcl) (`oidc_clients."opnsense-admin"`, PKCE on); secret in the 1Password item `keycloak-oidc-opnsense-admin#dev`; redirect URI `https://gw3.home.iseja.net/api/sso/oidc/callback` |
| Server (`System ‣ Access ‣ Servers`) | type OpenID Connect, name `keycloak-dev`, issuer `https://dev-auth.dev.iseja.net/realms/admin`, scopes `openid,profile,email,groups`, PKCE S256, username claim `preferred_username`, applies to `webgui` only, automatic user creation off, strict account binding on (default), base URL `https://gw3.home.iseja.net` |
| Added without the GUI | at the owner's request the server was written to `config.xml` by a small PHP script that mirrors `system_authservers.php` (same defaults and validators, `write_config()`), the secret passed on stdin from 1Password, never on a command line |
| Local account | `bob-adm`, uid 20000, in `admins`, no usable password. Created with the plugin's own account writer (`LocalAccountWriter::create`), because the plugin refuses to bind a login to an administrator account it did not create. |
| Login list | unchanged: `System ‣ Settings ‣ Administration ‣ Authentication ‣ Server` stays "Google Auth OTP" (the only entry on `gw3`, so `root` already needs password and local token) |

**Result.** The login page shows a "keycloak-dev" button. Pressing it redirects to Keycloak with the right client, redirect URI and PKCE challenge, and after logging in as `bob-adm` at Keycloak the log of `gw3` shows `Successful login for user 'bob-adm' via SSO (keycloak-dev)`. The first login stamps the Keycloak subject on the account (`sso_subject` next to the `sso_owned` marker), which is the binding for all later logins. The `root` login path was not changed at any point.

**Findings worth keeping.**

- The login button exists as soon as the server is saved, independent of the server list; the list ("Google Auth OTP") is irrelevant to the OIDC path.
- The plugin's "Test" button on the server only does the OIDC discovery, not a login. The actual proof is the login itself, which needs the local account first.
- A manually created administrator account does **not** work: it has to be created by the plugin (or exist already with the plugin's ownership stamp). A non-privileged account with a scrambled password and an exact username match would bind; an `admins` member that the plugin did not create is refused.
- In the audit log the configuration write at the login callback is attributed to `root@<client address>`, not to `bob-adm`: the callback has no session yet. Reading the audit log for "who changed this" is therefore misleading around SSO logins.
- The first login writes to `config.xml` (the binding stamp). On an HA backup this write is local and a later sync from the master may undo it; the binding is re-created at the next login.
- UIDs: `create()` takes the next free number and stamps the account against it, so a chosen uid (20000 here) is set via `nextuid` for the one call and `nextuid` restored.

**Not exercised.** A login with Keycloak unreachable (expected: the button fails, `root` + local TOTP works), group claims from UCS (`sec.app.opnsense.admin`), whether the owner was asked for the second factor during the test (the realm `admin` of `dev` requires one per [`keycloak-mfa.md`](keycloak-mfa.md), but the prompt was not observed), `gw2`, the HA master, and removing the plugin again.

## OIDC: towards production

Not done; needs the owner's go at each step (an authentication change on the firewall, a UCS group).

1. **Second factor and recovery**: the factor itself is enforced in the realm `admin` of `qa` and `prod` ([`keycloak-mfa.md`](keycloak-mfa.md), apply recorded there). Before relying on it for the firewall check that `bob-adm` has the hardware key enrolled in `prod` (the check was moved to [#2247](https://github.com/isejalabs/homelab/issues/2247)), and read [`keycloak-break-glass.md`](keycloak-break-glass.md) once with this dependency in mind. Set `max_age` on the server (see [Decision](#decision)) so that an existing Keycloak session does not replace the second factor.
2. **Production client**: a client in the prod `keycloak-realm` unit with the redirect URIs of every box that serves the login (the CARP name if the GUI is reached over it, plus each box's own name, `gw3` and `gw2`). The dev client of the proof of concept is replaced, not reused, and its secret item removed.
3. **UCS group** `sec.app.opnsense.admin` (members: `bob-adm`) as a gate: set "Required groups" on the server so that only that group may log in, and map it to the local `admins` group with the plugin's group map. A UCS change; not made.
4. **Install the plugin on `gw2`** (the master has none; a package is not synced) from the same pinned release, after the same comparison with the tagged source. Take a `config.xml` backup first.
5. **Server entry and accounts.** The authentication-server list is synced from the master, so the production entry is added on `gw2` and appears on `gw3` within seconds, **replacing the entry added by hand on `gw3`** (including the proof-of-concept one). To test before that, add the production entry on `gw3` by hand first, which the master's next sync then overwrites with the same entry. Accounts: the `<user>` entries are synced, but the plugin's ownership marker is kept in its own settings section, which is not synced, and an administrator account without the marker is refused. The marker is stored against the numeric user id, so the account is created with the plugin's writer on both boxes with **the same uid** (20000 on `gw3` already); then a synced user list matches the marker on the other box. Not yet observed. Each box stamps the Keycloak subject at its own first login.
6. **Outage behaviour to measure**: Keycloak down (the cluster, the hypervisor, an internet-independent path), the UCS federation down while Keycloak is up, the clock of the box (token validation). The answer for every case is `root` + local TOTP on the box, which this route never touches.
7. **Plugin upkeep**: single maintainer, version `2026.11.1`, no signed attestation. Updates are installed by hand after the same comparison with the tagged source; there is no Renovate or Flux for this. Reviewing a release is the owner's call.

## LDAP and local TOTP: configuration

The alternative route, kept in case the plugin is rejected. Not chosen: the token is typed in front of the password in one field, and the seed lives in every local user.

Planned content of [#2238](https://github.com/isejalabs/homelab/issues/2238); nothing of this is applied. UCS changes need the owner's explicit go, and no OPNsense setting is changed before the [test procedure](#ldap-and-local-totp-test-procedure-without-lock-out) has been followed.

**UCS** (as `root` on a domain controller, like the groups in [`keycloak-realms.md`](keycloak-realms.md#ucs-setup); names follow [`ucs-groups.md`](ucs-groups.md)):

- Groups `sec.app.opnsense.admin` (members: `bob-adm`), later `sec.app.opnsense.operator` and `sec.app.opnsense.readonly` ([#2239](https://github.com/isejalabs/homelab/issues/2239)). Accounts only, no nested groups (LDAP `memberOf` is direct only).
- A read-only bind account **`opnsense-ro`**, an ordinary user in no group, separate from `keycloak-ro` so each can be rotated and revoked alone. Its password is stored in 1Password and, because OPNsense keeps the bind password in `config.xml`, it also lives in the OPNsense configuration and in its backups. The account can read directory entries and nothing else.

**OPNsense** (configured on the HA master; the items users and groups, authentication servers and certificates are synced to the backup, see [High availability](#what-opnsense-can-do) above; `gw4` is not part of the pair, cannot reach the DCs on 7636 and keeps its local login):

1. `System ‣ Trust ‣ Authorities`: import the UCS CA (`/etc/univention/ssl/ucsCA/CAcert.pem`, the same certificate as in the 1Password item `ucs-ca`). Certificates are not among the ticked HA sync items, so import it on each box.
2. Name resolution of the DCs without UCS DNS: `Services ‣ Unbound DNS ‣ Overrides` with `baerbel.dir.iseja.net` (10.7.1.102) and `adelheid.dir.iseja.net` (10.7.1.101). The certificate check needs the name, and the name must resolve while UCS DNS is down, which is exactly the outage case (the DNS and LDAP dependency is otherwise circular for the login).
3. `System ‣ Access ‣ Servers`: two servers of type "LDAP + Timebased One Time Password", one per DC. Hostname as above, port 7636, transport SSL, protocol 3, bind DN `uid=opnsense-ro,cn=users,dc=dir,dc=iseja,dc=net`, search scope subtree, base DN `dc=dir,dc=iseja,dc=net`, user attribute `uid`, extended query `|(memberOf=cn=sec.app.opnsense.admin,cn=groups,dc=dir,dc=iseja,dc=net)(memberOf=cn=sec.app.opnsense.operator,...)(memberOf=cn=sec.app.opnsense.readonly,...)` (one clause per group that exists), "Read properties" and "Synchronize groups" on, "Limit groups" `sec.app.opnsense.admin,sec.app.opnsense.operator,sec.app.opnsense.readonly`, automatic user creation **off**, token length 6.
4. `System ‣ Access ‣ Groups`: create the local groups with exactly these names; `sec.app.opnsense.admin` gets the privilege "All pages".
5. `System ‣ Access ‣ Users`: create `bob-adm` (login shell `nologin`, "Scrambled Password" on, a generated OTP seed enrolled in the authenticator app). No group is set by hand: the first login attaches `sec.app.opnsense.admin`.
6. Only after steps 1 to 5 tested with `System ‣ Access ‣ Tester` (it shows `memberOf` in the returned properties), set `System ‣ Settings ‣ Administration ‣ Authentication ‣ Server` to the two LDAP servers followed by "Local Database".

**Second factor in practice.** `123456` + password in one field is awkward with a password manager. The "Reverse token order" option (password, then token) lets 1Password fill the password and the token be typed after it. If the seed, the UCS password and the passkey all live in one vault the factors collapse into "access to the vault", as noted for the Keycloak realm `admin` in the [design plan](../plans/2026-10-identity-claude.md); a hardware TOTP token avoids it.

**Accounts that bypass the second factor.** "Local Database" is in the list for everyone, so any local user with a usable password logs in with that password alone. Directory users therefore get scrambled passwords; `root` is the only local password account. A local user that is "disabled" in OPNsense is not refused by the LDAP authenticator, which does not look at that flag (source above); remove the group in UCS instead.

## LDAP and local TOTP: outage behaviour

| Situation | Result |
| --- | --- |
| One DC down | The failing server entry is skipped, the next one answers. Each unreachable DC costs a connect timeout of up to 30 s (`LDAP_OPT_NETWORK_TIMEOUT`); the Keycloak failover measured about 41 s per login, so expect something comparable here. |
| Both DCs or the UCS VLAN down | Both LDAP entries fail, "Local Database" answers: `root` logs in (after the timeouts, up to about a minute). If that is too slow, move "Local Database" to the first place: then `root` is immediate and a directory login costs one failed local check (the 2 s minimum of a failed attempt, `Base::authenticate()`). Decide with the measurement in the test procedure. |
| UCS DNS down | No effect for the login, because of the Unbound overrides above. Without them the name resolution fails and the login takes the timeout path. |
| Cluster or Keycloak down | No effect. OPNsense never talks to Keycloak. |
| Console and SSH | Same list as the web interface; `root` with its password or key, as before. |

Circular dependency: UCS depends on OPNsense (the gateway of its VLAN and the DHCP relay of every client network), and the OPNsense administrators depend on UCS. `root` breaks the loop, and the firewall's own routing, BGP and DHCP relay do not use LDAP at all.

Firewall rules: the LDAPS connection starts on the firewall itself, from the address of the interface towards the DC VLAN (the individual address of each box, not the CARP virtual address, unless an outbound NAT rule says otherwise). Locally originated traffic is passed by default; what has to be checked is the UCS side (packet filter on the DCs admits 7636 from both boxes).

## LDAP and local TOTP: test procedure without lock-out

For [#2238](https://github.com/isejalabs/homelab/issues/2238). The web-interface item that holds the server list is not synced (read on `gw2`), so the login list is changed per box and a wrong list can only lock out the box it was set on; change the backup first. Authentication servers and users are synced, which does no harm until a list points at them.

1. **Before anything:** open two browser sessions as `root` on the box (one stays open throughout, a private window is enough); confirm the console route (Proxmox VM console of the gateway) and that the `root` password from the vault works in a **third** fresh login. Export the configuration (`System ‣ Configuration ‣ Backups`) and keep it off the box.
2. Create CA, DNS overrides, servers, groups and the user as in [Configuration](#ldap-and-local-totp-configuration), **without** touching the `Authentication ‣ Server` setting. Use `System ‣ Access ‣ Tester` for `bob-adm` (password + token): it must authenticate, show the `memberOf` of `sec.app.opnsense.admin`, and an account outside the group (an everyday account, or another user) must fail with "User DN not found".
3. Set the server list to `LDAP, LDAP, Local Database` in the open `root` session and save. Do not log out of the other sessions.
4. In a new private window log in as `bob-adm` with token + password; check the privileges (all pages) and that the group is attached to the user. Log in as an account outside the group and as a user with the wrong token: both must fail. Check that a fresh `root` login still works.
5. **Outage test:** block the DC addresses for the box (a temporary floating rule on the box, removed afterwards, or unplug the DC VLAN link of a lab box), time a fresh `root` login and a `bob-adm` login (the latter must fail), and note the delay. Remove the block and confirm the directory login works again. Do not power off a DC for this ([#1821](https://github.com/isejalabs/homelab/issues/1821)).
6. If anything fails, in the open `root` session set the server back to "Local Database" only. If every session is lost, use the console menu option 3 "Reset the root password" or restore the exported configuration.
7. Repeat on the second box (or let the HA sync do it and repeat steps 4 and 5).

## Operator and read-only access

Decision for [#2239](https://github.com/isejalabs/homelab/issues/2239), to be confirmed once the chosen login route works with the real account. The privilege analysis holds for both routes (it is about OPNsense's page-level rights); with OIDC the group comes from the plugin's group map instead of LDAP `memberOf`:

- **OPNsense has no read-only or read/write separation.** A privilege grants URL patterns (`ACL.xml` in the 26.7.8 source), and a page that reads can usually also write. Evidence from the same source: "Status: Services" is `api/core/service/*` (start, stop, restart), "Diagnostics: Show States" includes `del_state`, `kill_states`, `flush_states`, the dashboard saves widgets into the user's configuration (`saveWidgetsAction`), and "Lobby: Password" would let a directory user set a local password and so bypass the second factor.
- **The owner's everyday account `bob` (operator): possible.** Candidate set of pages that only read or run a diagnostic that leaves no configuration behind: Lobby: Dashboard, Status: Interfaces, Diagnostics: Logs: System, Logs: Gateways, Firewall statistics, Routing tables, ARP and NDP tables, Netstat, System Health, Ping, Traceroute, Test Port (the ping job writes a temporary file, not the configuration). Not granted: Status: Services, Show States, Firewall sessions (pftop), Packet Capture, Lobby: Password, anything under Firewall, Interfaces, System: Access or Configuration. The firewall log views show every client's connections; for the owner's own account that is acceptable.
- **Other users (read-only): not granted.** There is no read-only privilege, and the pages that would be harmless show network internals (logs, routing, connections) of every user without a use for the account. This is the outcome the rollout rules allow ("no access if no safe role"); the group `sec.app.opnsense.readonly` is not created.
- The group `sec.app.opnsense.operator` is created when `bob` is enabled, with the page list above as privileges of the local group; the list is checked against the privilege names of the installed version first.

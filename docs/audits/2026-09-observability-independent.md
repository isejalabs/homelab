# Observability assessment — independent pass (September 2026)

**Date:** 2026-09-29. **Status:** Independent second assessment, produced for comparison; not a replacement. **Scope:** homelab metrics, capacity, logs, alerting, history and operating cost — the same brief as the owner's original request.

This assessment was produced from scratch, without reading the already-merged [`2026-09-observability.md`](2026-09-observability.md) assessment, its companion [plan](../plans/2026-09-observability.md), or issue #71's recorded discovery answers, at the owner's explicit request to compare two independent analyses of the same input. It draws only on the owner's original as-is/requirements write-up, four clarifying answers gathered directly in this session (recurring budget ceiling up to ~€5/month; top candidate-selection factor is low SSD/resource write footprint; outage-resilience approach is a minimal free external heartbeat rather than a full cloud stack; authentication-log retention target is 90 days), and fresh inspection of both repositories. Where a conclusion here matches the earlier assessment, treat that as independent convergence, not reuse — this pass deliberately avoided rereading that material first.

## Decision summary

Keep Checkmk as the infrastructure metrics, capacity-alerting and historical-graph system; nothing in either repository shows a working alternative already in place, and the repository's own architecture documentation confirms no Prometheus/Grafana pipeline is actually deployed. Prioritize closing the Longhorn-disk and RustFS-bucket capacity gaps ahead of any logging work, because Longhorn's default disk currently has zero reserved headroom — a full disk is a hard failure today, not a monitoring nicety. Bring loghost's own syslog-ng/logcheck configuration into Salt before or alongside adding any new logging component, since it currently is not version-controlled at all. Pilot a single-node, resource-light searchable log store (see candidate comparison) rather than hand-authoring a new logcheck-style ruleset from nothing. Satisfy the outage-resilience requirement by extending the backup stack's existing external heartbeat pattern rather than standing up a new cloud service.

## A clarification on SSD constraints that changes how candidates should be measured

Two distinct constraints were conflated in early framing and are worth separating explicitly, per the owner's own correction:

- **USB-attached backup disk spin-up avoidance.** The daily SMART/usage cadence exists specifically so these disks are not powered on more than necessary. This is a *frequency* concern tied to specific removable media, not a general rule for every disk in the fleet.
- **Always-on system SSD write endurance.** The Proxmox host boot/root SSDs (the ones hosting loghost, monitoring1/2 and other LXCs) can be polled as often as useful without a spin-up penalty — they never sleep — but every byte anything writes to them (journald, logging pipelines, a metrics/logging backend's WAL, indexes and compaction) consumes write endurance regardless of how often it is polled. This is the constraint behind the reported 203 TB-written, 91%-endurance-used SSD.

Any new logging/metrics component should therefore be evaluated on **measured bytes written per day**, not on poll interval — a candidate that polls rarely but writes a large compacted index on every flush can cost more endurance than one that polls often but writes compactly.

## Requirements re-read against this evidence

| Requirement | Assessment |
| --- | --- |
| Filesystem checks (WARN/CRIT, trends) | Longhorn's zero reserved headroom raises this from "close a visibility gap" to "the only thing between normal operation and a hard out-of-space failure" once additional workloads (e.g. Immich) land; RustFS buckets are equally ungated today. |
| Linux log collection | Already flowing to loghost correctly via rsyslog; the real gap is the unmanaged, non-version-controlled receiving side, not the transport. |
| Low SSD-sensitive writes | See the clarified two-part model above: USB backup-disk spin-up avoidance is already handled by the daily SMART cadence; always-on SSD write endurance depends on the bytes-written profile of whatever new component is added, which should be measured directly rather than inferred from polling frequency. |
| Availability during reboot | Optional; unaffected by any finding here. |
| Log checking | The existing logcheck ruleset is not only cumbersome but entirely untracked in git; any replacement belongs in Salt from the outset. |
| Alerting | No blocker found in either repository; depends on the logging backend chosen. |
| Long-term RRD graphs | Nothing in either repository contradicts keeping Checkmk for this, and there is no dormant Prometheus/Grafana pipeline that could take over even if desired (see the CRDs-only finding above). |
| Sources (Kubernetes events/pod logs, TrueNAS containers/services, OPNsense, Linux/UCS, authentication) | Kubernetes events and pod logs: genuinely zero collection today, since only metrics collectors run in-cluster. TrueNAS containers/services, OPNsense, Home Assistant/Immich/UCS authentication: all manual and unwired, matching the owner's inventory. |

On the owner's own question about whether investigations have needed more than etcd's roughly one-hour Events window plus `kubectl describe`/`--previous` logs: in general homelab-scale experience, that combination only really covers "the pod is still around and this is its most recent restart." Anything discovered after the fact — an overnight `CrashLoopBackOff` that had already resolved, an OOM-killed pod that was rescheduled, a node hiccup noticed the next morning — is exactly the case where that window has already closed by the time it is checked. For an environment that is reviewed periodically rather than watched live, that argues for at least a short-retention (even 24–72 hour) events-and-logs store, not for skipping one.

## Architecture and weighted candidate assessment

Weights, set from the owner's stated priorities in this session: SSD/resource footprint 35%, maintenance effort 25%, capacity/alerting coverage 20%, history/analysis depth 15%, outage resilience 5% (weighted low here because it can be satisfied cheaply on the side rather than through the primary backend choice — see below).

| Candidate | SSD/resource | Maintenance | Capacity/alerts | History/analysis | Verdict |
| --- | --- | --- | --- | --- | --- |
| Checkmk, extended with local Longhorn-disk and RustFS-bucket checks | High — local checks, no new store, reuses the existing 5-/15-minute cadence | Medium — RAW-edition manual host/folder work is a known, already-accepted cost | High once added | High — existing RRDs, roughly 700-day history untouched | Keep for metrics/RRD/alerting; close the two capacity gaps rather than replacing anything |
| Flat compressed logs plus a newly authored allow-list/digest script, in Salt | Highest — zero new components | Low in code, but requires authoring the same kind of regex rules that made the previous approach cumbersome | Low on its own — no query layer | Low — grep only | A reasonable version-controlled floor, but does not by itself answer the multi-source rollout requirement |
| VictoriaLogs, single node, on loghost | Good — columnar/compressed storage, generally lighter steady-state disk and memory than Loki at this scale for the same ingest volume | Medium — one additional service, but simple single-binary operation | Good — HTTP query API usable for alerting rules | Good for short/mid-term retention; not a substitute for RRDs | Best-fit pilot candidate given the stated top priority of write/resource footprint |
| Loki, single-binary, filesystem storage | Lower than VictoriaLogs at this scale due to index/chunk/WAL overhead | Medium-high — larger ecosystem than strictly needed here | Good | Good | Only preferable if the Grafana/Loki ecosystem is independently wanted later; not favored by the stated weighting |
| Full replicated in-cluster logging stack | Poor — additional replicated writes on already-loaded storage | High | Good | Good | Not justified at this scale or budget |

On outage resilience specifically: rather than adding a new cloud service, the cheapest option consistent with the two highest-weighted priorities is to extend what already exists. The backup stack already uses an external heartbeat pattern — `zrepl-healthcheck-hook.sh` pings out on success/failure, and the owner's own inventory notes healthchecks.io already covers borgbackup jobs. Adding a periodic dead-man's-switch check-in from Checkmk or loghost itself means a missed check-in (host down, power out, network down) triggers a notification through a channel reachable from outside the home network, at essentially no added resource or write cost, within the stated €0–5/month budget. A Grafana Cloud-style free tier would only be worth the larger integration if the requirement were live dashboards during an outage rather than an alert that something is down — the owner's own weighting (resilience last, footprint first) does not support that trade here.
